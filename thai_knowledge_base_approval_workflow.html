กระบวนการ 8 ขั้นตอน

1
Trigger Detection — ตรวจจับสถานะ reviewStatus = "draft"
Automatic System
▾

ระบบ MCP Layer ตรวจสอบ reviewStatus ทุกครั้งที่ Agent ทำ knowledge lookup และเมื่อ deploy ครั้งแรก หากพบ "draft" ระบบจะสร้าง Gate-1 Review Task อัตโนมัติและแจ้งเตือน SME Coordinator

🔎 Trigger Conditions
  • reviewStatus === "draft" ใน knowledge-export.json
  • Agent ส่ง low_confidence_warning ครั้งแรก
  • Deploy ใหม่หลัง import knowledge
  • Manual trigger โดย Programme Manager
📤 Output ของ Step นี้
  • Gate-1 Review Task สร้างแล้ว
  • แจ้งเตือนไปยัง SME Coordinator ทาง email/Line
  • Log entry: GATE1_REVIEW_INITIATED
  • Dashboard แสดง status: "Pending SME Assignment"
2
SME Assignment — กำหนด SME ตาม Domain
Manual Critical
▾

Programme Manager มอบหมาย SME ตาม subProcessGroup ของแต่ละ array ใน knowledge-export.json โดยต้องระบุ SME หลัก (Primary) และ SME สำรอง (Backup) พร้อมกำหนด deadline

👤 การแบ่ง Domain
  • Office Domain (Sale/Design/Planning): ผู้จัดการฝ่าย
  • Factory Domain (Production steps): หัวหน้าฝ่ายผลิต
  • Installation Domain: หัวหน้าทีมติดตั้ง
  • PFMEA Risk Rows: QA Manager (ทุก domain)
  • RACI Map cross-check: Programme Manager
⏰ SLA ที่ต้องปฏิบัติ
  • SME Assignment ต้องเสร็จภายใน 1 วันทำการ
  • Review processModel: ≤ 3 วันทำการ
  • Review pfmeaRiskRows: ≤ 5 วันทำการ
  • Review raciMap: ≤ 2 วันทำการ
  • Final Decision: ≤ 1 วันทำการหลัง review ครบ

Review processModel — ตรวจสอบ 28 Process Steps
Manual Review
▾

SME ตามแต่ละ subProcessGroup ตรวจสอบว่า processStep ถูกต้องตรงกับ Standard Operating Procedure ปัจจุบัน ครบทุก 28 ขั้นตอน ไม่มีขาด/เกิน/ซ้ำ

📋 Checklist — processModel
  • processStep ชื่อตรงกับ SOP ล่าสุด
  • subProcessGroup จัดหมวดหมู่ถูกต้อง (Office/Factory/Install)
  • canonicalOrder เรียงลำดับถูกต้อง (1–28)
  • requiresApproval ตั้งค่าถูก (true/false)
  • approvalQuorum สอดคล้องกับ RACI accountable
  • ไม่มี processStep ที่ซ้ำกัน
  • ครบ 28 steps ไม่ขาด
📊 subProcessGroup ที่ต้องครบ
  • Sale & Customer Intake
  • Design & Approval
  • Production Planning
  • Material Procurement
  • Factory Production (Laminate→Packing)
  • Quality Control
  • Installation & Handover
4
Review pfmeaRiskRows — ตรวจสอบ 122 PFMEA Risk Rows
QA Review Critical
▾

QA Manager ตรวจสอบ PFMEA Risk Rows ทุก 122 แถว โดยเน้นที่ Severity ≥ 7 เป็นพิเศษ ต้องตรวจว่า Control Measures ที่ระบุยังสอดคล้องกับ Process ปัจจุบัน และ Detection Method ทำได้จริง

📋 Checklist — pfmeaRiskRows
  • Severity Rating (1–10) ถูกต้องตามความรุนแรงจริง
  • Occurrence Rating สะท้อนความถี่จริงในปัจจุบัน
  • Detection Rating ตรงกับความสามารถตรวจจับจริง
  • RPN = Sev × Occ × Det คำนวณถูกต้อง
  • Control Measures ยังใช้งานได้ (ไม่ obsolete)
  • Sev=9 rows มี Action Required ที่ชัดเจน
  • Recommended Actions สอดคล้องกับ SOP
🚨 Focus Areas — High Severity
  • Sev=9: ตรวจทุก row (Critical) — Actions ต้องมี owner
  • Sev=8: ตรวจ Control Measures ครบถ้วน
  • Sev=7: ตรวจ Detection Method ว่าทำได้จริง
  • RPN ≥ 200: Priority review & escalation path
  • New risks ที่เกิดจาก AI Agent process ต้องเพิ่ม
5
Review raciMap — ตรวจสอบ 28 RACI Entries
RACI Review
▾

Programme Manager ร่วมกับ Domain Leads ตรวจสอบ RACI Map ทุก 28 entries ว่า responsible/accountable/consulted/informed ถูกต้องและไม่ขัดแย้งกัน โดยเฉพาะ entries ที่มี approvers field

📋 Checklist — raciMap
  • ทุก entry มี responsible (ผู้ทำ) ชัดเจน
  • accountable เป็นผู้จัดการระดับ Manager ขึ้นไป
  • ไม่มีบุคคลเดียวเป็นทั้ง responsible และ accountable
  • consulted list ครบ (ไม่ขาดผู้ที่ต้องให้ input)
  • informed list ถูกต้อง (ผู้รับทราบแต่ไม่ตัดสิน)
  • approvers field ตรงกับ requiresApproval=true ใน processModel
  • approvalQuorum ตรงกับนโยบาย (unanimous/majority/first_response)
✅ Approval-Required Steps ต้องตรวจพิเศษ
  • Design Approval: approvers=[ผู้จัดการออกแบบ, ลูกค้า] — quorum=unanimous
  • Production Plan Approval: approvers=[ผู้จัดการผลิต, ผู้จัดการทั่วไป] — quorum=first_response
  • PO Approval: approvers=[ผู้จัดการฝ่ายจัดซื้อ, ผู้จัดการโครงการ]
  • QC Sign-off: approvers=[หัวหน้า QA, ผู้จัดการผลิต]
  • Installation Handover: approvers=[ลูกค้า, หัวหน้าทีมติดตั้ง]

SME Decision — Approve / Request Changes / Reject
Decision Point Gate
▾

หลัง SME review ครบ 3 sections SME แต่ละคนส่ง Review Report พร้อมคำแนะนำ Programme Manager รวบรวมและตัดสิน: Approve (ทุก SME ไม่มีข้อบกพร่องร้ายแรง) / Request Changes (มีแก้ไขบางส่วน) / Reject (ต้องทบทวน QMS ใหม่)

📊 Approval Criteria
  • SME ทุกคนต้อง Sign off — ไม่มี Critical Issue
  • Sev=9 PFMEA rows ทุก row มี Control Measure
  • RACI ไม่มี gap ในขั้นตอน requiresApproval
  • processModel ตรงกับ SOP ปัจจุบัน 100%
  • ไม่มี Minor Issue เกิน 5 ข้อ (ถ้ามีให้ Request Changes)
📝 Review Report ต้องระบุ
  • Section ที่ตรวจ (processModel/pfmea/raci)
  • จำนวน items ที่ตรวจ
  • Issues พบ (Critical/Minor)
  • คำแนะนำ (Approve/Request Changes/Reject)
  • ลายเซ็น SME และ วันที่

Decision Flow — Approve / Request Changes / Reject

🔀 เส้นทางการตัดสินใจหลัง SME Review ครบ

✅ APPROVE
  1. SME ทุกคน sign off ไม่มี Critical Issue
  2. Programme Manager ออก Approval Record
  3. อัปเดต reviewStatus → "approved"
  4. Bump sourceVersion → "daph-qms-2026-rev01"
  5. Push ไป GitHub branch main
  6. รัน Re-Embed Script
  7. Gate-1: PASS ✅
📝 REQUEST CHANGES
  1. SME ระบุ items ที่ต้องแก้ไข (Minor Issues)
  2. Programme Manager ส่ง Change Request
  3. Content Owner แก้ไข knowledge-export.json
  4. SME ตรวจสอบ items ที่แก้ไขแล้ว
  5. ถ้า OK → กลับไป Approve Decision
  6. ถ้า Round > 2 → Escalate ถึง Management
  7. Gate-1: รอ PASS ⏳
❌ REJECT
  1. พบ Critical Issues ที่แก้ไขไม่ได้ใน JSON
  2. Programme Manager ออก Rejection Report
  3. ส่งกลับ QMS Team เพื่อ revise source documents
  4. Re-export knowledge จาก QMS ใหม่
  5. เริ่ม Review Process ใหม่ตั้งแต่ Step 1
  6. ETA: ตกลง timeline ใหม่กับ Management
  7. Gate-1: BLOCKED 🚫

Version Control Procedure

🏷️ การอัปเดต sourceVersion หลัง Approval

ปัจจุบัน (Draft)
daph-qms-2020-rev00
→
หลัง Approval
daph-qms-2026-rev01
📐 Version Naming Convention
  • Format: daph-qms-{YYYY}-rev{NN}
  • {YYYY} = ปีที่ review/approve (2026)
  • {NN} = revision number 2 digits (เริ่มที่ 01)
  • Patch update (minor corrections ≤5 items): bump rev เท่านั้น เช่น rev01→rev02
  • Major update (เพิ่ม/ลบ process steps): bump year + reset rev เช่น 2027-rev01
  • ทุก version bump ต้องมี changelog entry ใน knowledge-export.json
  • GitHub: tag knowledge-v2026-rev01 ที่ commit นั้น
